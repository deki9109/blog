클라우드 복원력은 이제 선택 기능이 아니라 기본 아키텍처 요구사항이 됐습니다. 서비스가 클라우드 위에서 운영되는 시간이 길어질수록 장애는 피할 수 없는 전제가 됩니다. 특정 리전, 네트워크 경로, 관리형 데이터베이스, 인증 시스템, 메시지 큐, 외부 API 중 하나만 흔들려도 사용자 경험은 바로 영향을 받습니다.

최근 클라우드 공급자들은 멀티 리전 실행, 교차 리전 백업, 데이터 복제, 장애 전환 기능을 계속 강화하고 있습니다. 하지만 중요한 점은 기능이 있다는 것과 조직이 복원력을 갖췄다는 것은 다르다는 사실입니다. 복원력은 설정값 하나가 아니라 어떤 서비스를 얼마나 빨리, 어떤 품질로, 어떤 데이터 손실 한도 안에서 살릴지 정하는 운영 설계입니다.

## 멀티 리전은 시작점일 뿐이다

멀티 리전 배포는 강력한 도구지만 자동으로 안전을 보장하지 않습니다. 애플리케이션 서버만 여러 리전에 두고 데이터베이스, 인증, 결제, 파일 저장소, 검색 인덱스가 한 리전에 묶여 있으면 실제 장애 전환은 제한됩니다. 사용자는 웹 화면이 열리는지만 보지 않습니다. 로그인, 주문, 검색, 알림, 고객 지원까지 함께 작동해야 서비스가 살아 있다고 느낍니다.

따라서 첫 단계는 의존성 인벤토리입니다. 주요 사용자 여정별로 어떤 컴포넌트가 필요한지, 각 컴포넌트가 어느 리전에 있는지, 대체 경로가 있는지, 장애 시 어떤 기능을 포기할 수 있는지 정리해야 합니다. 전체 서비스를 한 번에 완벽히 살리려 하면 비용과 복잡도가 커집니다. 대신 최소 운영 서비스, 읽기 전용 모드, 지연 허용 기능, 일시 중단 기능을 나눠야 합니다.

예를 들어 결제는 막히더라도 기존 주문 조회와 고객 공지는 살아 있어야 할 수 있습니다. 실시간 분석은 멈춰도 핵심 거래는 유지해야 할 수 있습니다. 이 구분이 없으면 장애 상황에서 모든 팀이 같은 우선순위로 움직이지 못합니다.

## RTO와 RPO는 문서가 아니라 설계 입력이다

RTO는 얼마나 빨리 복구할지, RPO는 얼마나 많은 데이터 손실을 허용할지에 대한 기준입니다. 많은 조직이 이 수치를 문서에 적어두지만 실제 아키텍처와 테스트에 반영하지 못합니다. 15분 RTO를 말하면서 수동 DNS 변경, 수동 데이터베이스 승격, 수동 권한 승인이 필요한 구조라면 실제 복구 시간은 더 길어질 가능성이 큽니다.

RPO도 마찬가지입니다. 교차 리전 백업이 있어도 백업 주기, 복제 지연, 복원 검증, 애플리케이션 재연결 절차가 명확하지 않으면 데이터 복구는 늦어집니다. 백업은 존재만으로 충분하지 않습니다. 정기적으로 복원해보고, 복원된 데이터로 서비스가 실제 동작하는지 확인해야 합니다.

또 하나의 현실적인 문제는 데이터 일관성입니다. 모든 데이터를 모든 리전에 실시간으로 완벽히 맞추려 하면 비용과 지연 시간이 커질 수 있습니다. 그래서 계정, 결제, 주문처럼 강한 일관성이 필요한 데이터와 로그, 분석, 추천처럼 지연을 허용할 수 있는 데이터를 분리해야 합니다.

## 운영 리허설이 없으면 복원력은 추정치다

복원력은 장애가 나기 전에는 대부분 추정입니다. 실제로 검증하려면 리허설이 필요합니다. 특정 리전 장애, 데이터베이스 지연, 큐 적체, 인증 장애, 외부 API 실패, 배포 시스템 중단 같은 시나리오를 정해 실행해봐야 합니다. 여기서 목적은 장애를 만드는 것이 아니라 조직이 어떤 순서로 판단하고 복구하는지 확인하는 것입니다.

리허설에는 기술팀만 참여하면 부족합니다. 제품, 고객지원, 보안, 법무, 영업 운영도 영향을 받습니다. 고객에게 어떤 상태를 알릴지, 어떤 기능을 제한할지, 어떤 데이터 처리 작업을 멈출지, 사후 보고에 어떤 로그가 필요한지 함께 정해야 합니다.

관측성도 복원력의 핵심입니다. 장애 상황에서는 평균 지표보다 사용자 여정별 상태가 중요합니다. 로그인 성공률, 결제 성공률, 주문 조회 지연, 백업 최신성, 복제 지연, 큐 적체, 리전별 오류율을 한눈에 볼 수 있어야 합니다. 경보가 너무 많아도 문제입니다. 장애 전환 중에는 어떤 경보가 의사결정에 필요한지 구분돼 있어야 합니다.

![SRE와 플랫폼 팀이 클라우드 장애 이후 복원력 아키텍처와 런북을 검토하는 회의 장면](/images/2026-07-26-cloud-resilience-architecture-sub2.png)

오늘 기준으로 운영팀이 정해야 할 항목은 다섯 가지입니다.

1. 사용자 여정별 의존성 인벤토리를 만들고 단일 리전 병목을 표시해야 합니다.
2. RTO/RPO를 문서가 아니라 백업 주기, 복제 구조, 자동화 수준, 테스트 주기에 연결해야 합니다.
3. 전체 서비스 복구만 목표로 하지 말고 최소 운영 모드와 읽기 전용 모드를 설계해야 합니다.
4. 교차 리전 백업은 정기 복원 테스트까지 포함해야 실제 가치가 있습니다.
5. 장애 전환 리허설을 기술팀, 제품팀, 고객지원팀이 함께 수행해야 합니다.

클라우드 복원력은 더 많은 리전을 쓰는 경쟁이 아닙니다. 어떤 장애를 받아들일지, 어떤 기능을 먼저 살릴지, 어떤 데이터 손실을 허용하지 않을지 명확히 정하는 작업입니다. 기능은 클라우드가 제공할 수 있지만, 우선순위와 책임 구조는 조직이 직접 설계해야 합니다.
