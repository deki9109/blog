포스트 양자 암호는 더 이상 연구실 안의 주제가 아닙니다. NIST는 2024년에 ML-KEM, ML-DSA, SLH-DSA를 첫 포스트 양자 암호 표준으로 확정했습니다. 표준이 나왔다는 것은 모든 시스템을 즉시 바꾸라는 뜻은 아닙니다. 하지만 어떤 시스템이 어떤 암호를 쓰는지 모르는 상태로 기다릴 수 있는 단계도 지났습니다.

핵심은 "새 알고리즘을 어디에 넣을까"가 아니라 "우리 조직 안에 어떤 암호 의존성이 숨어 있는가"입니다. TLS, VPN, 코드 서명, 인증서, 데이터베이스 암호화, 백업, 펌웨어 업데이트, HSM, 임베디드 장비까지 살펴봐야 합니다. 포스트 양자 전환은 보안 프로젝트이면서 동시에 인벤토리, 배포, 성능, 호환성, 공급망 관리 프로젝트입니다.

## 위협은 먼 미래처럼 보이지만 데이터는 오늘 수집된다

양자컴퓨터가 언제 현재 공개키 암호를 실질적으로 위협할지는 여전히 불확실합니다. 그렇다고 대응을 미룰 수만은 없습니다. 이유는 "지금 훔치고 나중에 해독하는" 위험 때문입니다. 공격자가 오늘 암호화된 트래픽이나 민감 데이터를 수집해 두고, 나중에 충분한 양자컴퓨팅 능력이 생겼을 때 복호화를 시도할 수 있습니다.

모든 데이터가 같은 위험을 갖지는 않습니다. 하루나 일주일 뒤 가치가 사라지는 데이터와 10년 이상 보호해야 하는 의료, 금융, 정부, 지식재산 데이터는 다릅니다. 그래서 전환 우선순위는 시스템의 노출도뿐 아니라 데이터 보존 기간과 규제 요구사항까지 함께 봐야 합니다.

실무적으로는 장기 기밀성이 필요한 데이터 경로부터 확인해야 합니다. 외부 인터넷 TLS, 파트너 연동 API, 원격 접속, 내부 서비스 메시, 장기 백업, 데이터 레이크, 로그 보관소가 대표적입니다. 포스트 양자 전환은 가장 눈에 잘 띄는 웹 서버만 바꾸는 작업이 아닙니다.

## 첫 단계는 암호 자산 인벤토리다

대부분의 조직은 애플리케이션 목록보다 암호 목록이 훨씬 부정확합니다. 어떤 라이브러리가 RSA를 쓰는지, 어떤 장비가 ECC 인증서만 지원하는지, 어떤 배치 시스템이 오래된 TLS 스택을 쓰는지, 어떤 서명 체계가 빌드 파이프라인에 묶여 있는지 한 번에 알기 어렵습니다.

따라서 첫 작업은 암호 자산 인벤토리입니다. 서비스, 인증서, 키 길이, 알고리즘, 라이브러리, 프로토콜 버전, 장비 모델, 공급업체 지원 계획, 데이터 보존 기간, 교체 난이도를 같은 표에 올려야 합니다. 이 목록이 없으면 포스트 양자 전환은 범위를 알 수 없는 프로젝트가 됩니다.

여기서 중요한 것은 완벽한 목록을 기다리지 않는 것입니다. 인터넷 노출 시스템, 장기 보존 데이터, 인증서 자동화 경로, 코드 서명 체계처럼 위험이 큰 영역부터 시작해야 합니다. 이후 스캔, SBOM, CMDB, 클라우드 자산 목록, 인증서 투명성 로그, 런타임 텔레메트리를 결합해 정확도를 높이는 방식이 현실적입니다.

## 하이브리드 배포는 호환성 검증이 핵심이다

NIST 표준이 나왔어도 실제 전환은 단계적으로 진행됩니다. 특히 인터넷 프로토콜에서는 기존 ECC나 RSA 기반 체계와 포스트 양자 키 교환을 함께 쓰는 하이브리드 방식이 중요합니다. 하이브리드는 새 알고리즘 하나에만 의존하지 않고, 기존 보안성과 포스트 양자 내성을 동시에 확보하려는 전환 전략입니다.

문제는 패킷 크기, 핸드셰이크 지연 시간, 중간 장비 호환성, 오래된 클라이언트 지원입니다. 포스트 양자 키 교환은 기존 방식보다 메시지가 커질 수 있고, 일부 프록시나 보안 장비는 예상보다 큰 핸드셰이크를 제대로 처리하지 못할 수 있습니다. 그래서 전면 교체보다 카나리 배포와 계측이 중요합니다.

Cloudflare는 2026년에 모든 무료 영역에서 포스트 양자 키 합의를 기본으로 활성화하는 계획을 공개했습니다. 이런 움직임은 전환이 연구 단계가 아니라 인터넷 엣지의 운영 단계로 들어가고 있음을 보여줍니다. 다만 조직 내부 시스템까지 자동으로 준비되는 것은 아닙니다. 외부 엣지, 내부 서비스, 파트너 연동은 각각 따로 검증해야 합니다.

## 성능 지표 없이 암호를 바꾸면 장애를 만든다

암호 전환은 보안 강도만 보며 진행하면 안 됩니다. TLS 핸드셰이크 실패율, 연결 설정 시간, CPU 사용량, 메모리 사용량, 패킷 크기, 재전송, 지역별 지연 시간, 클라이언트별 오류율을 함께 봐야 합니다. 보안팀만의 작업이 아니라 SRE와 플랫폼팀이 같이 운영해야 하는 이유입니다.

가장 안전한 접근은 관측 가능한 실험입니다. 일부 도메인, 일부 리전, 일부 클라이언트 그룹에 하이브리드 키 교환을 적용하고 실패율과 지연 시간을 비교합니다. 문제가 생기면 즉시 롤백할 수 있어야 하고, 어떤 클라이언트나 중간 장비가 실패하는지 식별할 수 있어야 합니다.

코드 서명과 펌웨어 업데이트도 별도 주의가 필요합니다. 서명 알고리즘은 배포 체인 전체와 검증 장치가 함께 바뀌어야 합니다. 서버는 바꿨는데 오래된 디바이스가 새 서명을 검증하지 못하면 보안 강화가 아니라 업데이트 중단이 됩니다.

## 지금 해야 할 일은 명확하다

첫째, 암호 자산 인벤토리를 만든다. 알고리즘, 키, 인증서, 라이브러리, 프로토콜, 장비, 데이터 보존 기간을 함께 기록해야 한다. 둘째, 장기 기밀성이 필요한 데이터 경로를 우선순위로 둔다. 셋째, 인터넷 노출 TLS와 내부 서비스 메시에서 하이브리드 배포 실험을 준비한다.

넷째, 공급업체에 포스트 양자 지원 일정을 요구한다. HSM, WAF, CDN, VPN, MDM, 데이터베이스, 백업, 코드 서명 도구가 언제 어떤 표준을 지원하는지 확인해야 한다. 다섯째, 성능과 실패율을 기준으로 배포한다. 포스트 양자 암호는 체크박스가 아니라 운영 변경입니다.

오늘 기준으로 정리하면 세 가지입니다.

1. 포스트 양자 암호 전환은 알고리즘 교체보다 먼저 암호 자산을 찾는 작업입니다.
2. 장기 보존 데이터와 인터넷 노출 경로는 "나중에 해독" 위험 때문에 우선순위가 높습니다.
3. 실제 배포는 하이브리드 방식, 카나리, 텔레메트리, 롤백 계획을 갖춘 인프라 프로젝트로 다뤄야 합니다.

표준은 출발선입니다. 조직이 준비됐다는 뜻은 아닙니다. 준비됐다는 것은 어떤 암호를 어디서 쓰는지 알고, 어떤 데이터가 얼마나 오래 보호돼야 하는지 알고, 바꿨을 때 어떤 클라이언트와 장비가 깨지는지 검증할 수 있다는 뜻입니다. 포스트 양자 시대의 첫 번째 보안 역량은 더 강한 암호가 아니라, 암호를 운영 가능한 자산으로 관리하는 능력입니다.
