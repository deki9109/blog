AI 클러스터에서 Kubernetes를 쓰는 팀이 늘었지만, GPU 운영은 여전히 단순하지 않습니다. CPU와 메모리처럼 수량만 요청하면 끝나는 자원이 아니기 때문입니다. GPU 모델, 메모리 용량, MIG 파티션, NUMA 위치, 고속 NIC, 로컬 NVMe, 드라이버 버전, 토폴로지까지 성능과 실패율에 영향을 줍니다.

Kubernetes Dynamic Resource Allocation, 줄여서 DRA는 이런 특수 하드웨어를 더 명시적으로 다루기 위한 구조입니다. Kubernetes 1.34 릴리스에서 DRA 핵심 API는 GA가 됐고, 워크로드가 필요한 장치 속성을 더 풍부하게 표현하고 스케줄러가 그 요청을 기반으로 장치를 배정할 수 있는 기반이 강화됐습니다. AI 인프라 입장에서는 GPU를 "개수"가 아니라 "조건을 가진 자원"으로 운영하는 방향에 가깝습니다.

## GPU는 같은 GPU가 아니다

Kubernetes에서 전통적인 extended resources는 `nvidia.com/gpu: 1`처럼 수량 중심으로 장치를 요청하는 데 유용했습니다. 하지만 AI 워크로드가 복잡해지면서 단순 개수만으로는 부족한 경우가 많아졌습니다. 같은 GPU 한 장이라도 메모리 용량, 파티션 구성, 연결된 NIC, 드라이버 상태, 같은 노드 안의 다른 장치와의 거리 차이가 큽니다.

예를 들어 학습 작업은 여러 GPU 간 통신 토폴로지가 중요하고, 추론 작업은 특정 크기의 GPU 메모리와 안정적인 배치 밀도가 중요합니다. 검색 증강 생성 서비스는 GPU뿐 아니라 NVMe와 네트워크 대역폭이 함께 필요할 수 있습니다. 멀티테넌트 환경에서는 같은 물리 GPU를 나누는 정책도 중요합니다.

DRA의 의미는 이런 요구사항을 더 구조적으로 표현할 수 있다는 점입니다. 워크로드는 필요한 장치 조건을 선언하고, 클러스터는 실제 장치 상태와 정책을 고려해 배치합니다. 플랫폼팀은 장치 드라이버, 리소스 클래스, 클레임, 스케줄링 정책을 통해 하드웨어 사용 방식을 코드화할 수 있습니다.

## 장치 요청은 배포 단위와 분리되어야 한다

AI 서비스 운영에서 흔한 문제는 애플리케이션 매니페스트 안에 하드웨어 가정이 너무 많이 들어가는 것입니다. 특정 GPU 모델이나 노드 이름, 라벨 조합에 애플리케이션이 직접 묶이면 플랫폼을 바꾸기 어렵습니다. 노드가 교체되거나 새 GPU가 들어오면 서비스 매니페스트도 함께 흔들립니다.

DRA는 장치 요청과 실제 장치 배정을 분리하는 데 도움이 됩니다. 애플리케이션은 필요한 성능과 장치 조건을 선언하고, 플랫폼은 어떤 장치 풀에서 어떤 방식으로 배정할지 관리합니다. 이는 클라우드의 스토리지 클래스와 비슷한 사고방식입니다. 개발자는 목적을 말하고, 플랫폼은 구현을 책임집니다.

이 구조가 잘 작동하려면 플랫폼팀이 리소스 클래스를 명확히 설계해야 합니다. 예를 들어 대화형 추론용, 배치 추론용, 대규모 학습용, 실험용, 저비용 야간 작업용을 구분할 수 있습니다. 중요한 것은 이름만 나누는 것이 아니라 실제 장치 속성, 격리 수준, 비용 정책, 우선순위가 같이 정의되는 것입니다.

## 스케줄링 실패를 제품 문제로 봐야 한다

AI 클러스터에서 스케줄링 실패는 단순 인프라 이벤트가 아닙니다. 추론 서비스가 GPU를 못 잡으면 지연 시간이 늘고, 학습 작업이 대기하면 연구와 제품 실험 속도가 느려집니다. 특정 GPU만 계속 포화되거나, 고성능 장치가 저가치 작업에 묶이면 비용 효율도 떨어집니다.

DRA를 도입하면 장치 요청이 더 명시적이 되는 만큼 관측성도 중요해집니다. 어떤 ResourceClaim이 대기 중인지, 어떤 장치 속성 때문에 배치가 실패했는지, 특정 노드나 장치 클래스가 병목인지, 실제 사용률과 요청 조건이 맞는지 확인해야 합니다. 배정이 더 정교해질수록 실패 원인도 더 정교하게 봐야 합니다.

운영 대시보드는 GPU 사용률만 보여주면 부족합니다. 요청 대비 할당률, 대기 시간, 실패한 클레임 유형, 장치 클래스별 포화도, 노드별 열 상태, 드라이버 오류, 비용 대비 처리량을 함께 봐야 합니다. 플랫폼팀이 이 데이터를 보지 못하면 DRA는 유연성이 아니라 복잡도로 느껴질 수 있습니다.

## AI 워크로드에는 정책이 필요하다

특수 하드웨어는 비쌉니다. 그래서 누가 어떤 조건에서 어떤 GPU를 쓸 수 있는지 정책이 필요합니다. 모든 팀이 최고급 GPU를 기본값으로 쓰면 비용은 빠르게 늘고, 정작 필요한 작업이 대기합니다. 반대로 너무 강한 제한을 걸면 개발 속도가 떨어집니다.

현실적인 방식은 워크로드 유형별 정책입니다. 온라인 추론은 지연 시간과 안정성을 우선하고, 배치 추론은 비용과 처리량을 우선합니다. 실험 작업은 선점 가능 자원을 쓰고, 장기 학습은 예약과 쿼터를 둡니다. GPU 메모리가 작은 모델은 작은 파티션에 배치하고, 큰 모델은 전용 장치 풀에 배치합니다.

DRA는 이런 정책을 Kubernetes 리소스 모델 안에서 표현하는 기반을 제공합니다. 하지만 정책 자체를 자동으로 만들어주지는 않습니다. 조직은 비용 배분, 우선순위, 격리 수준, 승인 절차, 장애 대응 기준을 직접 정해야 합니다. 기술 기능보다 운영 규칙이 먼저입니다.

## 도입 전 확인할 것

첫째, 현재 GPU 사용 패턴을 측정해야 합니다. 어떤 워크로드가 어떤 장치를 얼마나 쓰는지, 대기 시간이 어디서 발생하는지, GPU 메모리 부족과 네트워크 병목이 얼마나 잦은지 알아야 합니다. 둘째, 장치 클래스를 정의해야 합니다. 모델명만이 아니라 용도, 비용, 격리, 성능 기대치를 함께 정의해야 합니다.

셋째, 드라이버와 벤더 플러그인 성숙도를 확인해야 합니다. DRA는 Kubernetes API와 스케줄링 기반을 제공하지만, 실제 장치 지원은 드라이버와 플러그인 생태계에 의존합니다. 넷째, 롤백 계획이 있어야 합니다. GPU 운영 경로를 바꾸는 작업은 배치 실패와 성능 회귀를 만들 수 있습니다.

다섯째, 관측성과 알림을 먼저 준비해야 합니다. ResourceClaim 대기, 장치 할당 실패, 특정 클래스 포화, 노드 드라이버 오류, GPU 열 스로틀링은 모두 운영 알림 대상입니다. AI 플랫폼에서 "배치되지 않음"은 곧 제품 지연입니다.

![플랫폼팀이 Kubernetes AI 클러스터의 GPU 할당률, 장치 대기열, 스케줄링 실패, 노드 용량, 열 상태, 비용 사용률을 모니터링하는 운영 대시보드 이미지](/images/2026-08-26-kubernetes-dra-ai-clusters-sub2.png)

오늘 기준으로 정리하면 세 가지입니다.

1. Kubernetes DRA는 GPU와 NIC 같은 특수 장치를 수량보다 조건 중심으로 요청하고 배치하는 기반입니다.
2. AI 클러스터에서는 장치 요청, 비용 정책, 스케줄링 실패, 관측성을 함께 설계해야 합니다.
3. 도입 효과는 API 사용 여부가 아니라 장치 클래스, 드라이버 성숙도, 운영 지표, 롤백 계획에서 결정됩니다.

AI 인프라의 다음 병목은 모델만이 아닙니다. 모델이 필요한 하드웨어를 제때, 올바른 위치에서, 적절한 비용으로 받을 수 있는지가 중요해집니다. DRA는 그 문제를 Kubernetes 안에서 더 명확히 표현하는 도구입니다. 하지만 성공 조건은 여전히 운영입니다. 어떤 장치를 누구에게, 언제, 어떤 기준으로 줄 것인지 명확히 해야 합니다.
