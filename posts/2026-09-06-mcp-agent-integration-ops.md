AI 에이전트가 실제 업무를 하려면 모델만으로는 부족합니다. 문서를 읽고, 일정과 메일을 확인하고, 데이터베이스를 조회하고, 코드를 실행하고, 티켓을 만들고, 배포 상태를 확인해야 합니다. 이때 필요한 것이 도구 통합입니다. Model Context Protocol, 즉 MCP가 주목받는 이유도 여기에 있습니다.

MCP는 애플리케이션이 모델에 컨텍스트와 도구를 제공하는 방식을 표준화하려는 프로토콜입니다. 하지만 프로덕션에서 중요한 질문은 "MCP를 붙였는가"가 아닙니다. 어떤 MCP 서버를 신뢰할지, 어떤 도구를 노출할지, 읽기와 쓰기 권한을 어떻게 나눌지, 위험한 작업은 어떻게 승인할지, 실행 기록을 어떻게 남길지가 핵심입니다.

## MCP 서버는 단순 플러그인이 아니다

MCP 서버는 모델이 사용할 수 있는 도구, 리소스, 프롬프트 같은 기능을 제공합니다. 겉으로 보면 플러그인처럼 보이지만, 실제로는 에이전트가 외부 시스템에 접근하는 신뢰 경계입니다. 파일 시스템, 코드 저장소, 사내 문서, 고객 데이터, SaaS 계정과 연결될 수 있기 때문입니다.

따라서 MCP 서버를 추가할 때는 기능 목록보다 신뢰 모델을 먼저 봐야 합니다. 서버를 누가 만들었는지, 어떤 인증 정보를 쓰는지, 어떤 네트워크로 접근하는지, 어떤 데이터를 반환하는지, 쓰기 작업을 수행할 수 있는지 확인해야 합니다. 신뢰할 수 없는 MCP 서버는 모델에게 악의적 도구 설명이나 오염된 컨텍스트를 제공할 수 있습니다.

MCP의 장점은 통합 방식이 일관된다는 점입니다. 그러나 일관된 통합은 일관된 위험도 함께 가져옵니다. 하나의 에이전트가 여러 MCP 서버를 동시에 쓰면 권한 범위가 빠르게 커집니다. 그래서 서버 단위, 도구 단위, 사용자 단위로 접근 범위를 제한해야 합니다.

## 도구는 많이 노출할수록 좋은 것이 아니다

에이전트에 도구를 많이 붙이면 능력이 커지는 것처럼 보입니다. 실제 운영에서는 반대가 될 수 있습니다. 도구가 많아질수록 모델이 잘못된 도구를 고르거나, 불필요한 호출을 하거나, 위험한 쓰기 작업을 시도할 가능성이 늘어납니다.

좋은 MCP 운영은 도구 카탈로그를 그대로 열어두지 않습니다. 업무 흐름별로 필요한 도구만 노출하고, 읽기 전용 도구와 상태 변경 도구를 분리합니다. 예를 들어 고객 정보를 조회하는 도구와 환불을 실행하는 도구는 같은 권한으로 다뤄서는 안 됩니다. 조회는 자동화할 수 있어도 환불, 삭제, 전송, 배포 같은 작업은 추가 확인이 필요합니다.

OpenAI의 MCP 관련 문서도 tool filtering, approval, tracing 같은 운영 요소를 함께 다룹니다. 이는 도구 연결이 단순 API 호출 문제가 아니라 에이전트 행동 통제 문제라는 뜻입니다. 모델이 도구를 호출할 수 있다는 사실보다, 어떤 조건에서 호출할 수 있는지가 더 중요합니다.

## 인증 정보는 사용자 의도와 분리하면 안 된다

MCP 서버가 외부 시스템에 접근하려면 인증 정보가 필요합니다. 문제는 에이전트가 이 인증 정보를 대신 사용한다는 점입니다. 사용자가 직접 버튼을 누르는 것과 모델이 추론 끝에 도구를 호출하는 것은 위험도가 다릅니다.

읽기 작업도 민감할 수 있습니다. 문서 검색, 메일 조회, 저장소 이슈 읽기는 내부 정보 유출로 이어질 수 있습니다. 쓰기 작업은 더 엄격해야 합니다. 메시지 전송, 파일 수정, 티켓 생성, 결제, 배포, 계정 변경은 사용자의 명시적 승인이나 정책 기반 제한이 필요합니다.

실무적으로는 세 가지 원칙이 필요합니다. 첫째, 기본 권한은 최소화합니다. 둘째, 위험한 도구는 호출 전 승인 절차를 둡니다. 셋째, 사용자가 승인한 범위와 에이전트가 실제로 수행한 작업을 감사 로그로 남깁니다. 권한이 넓은 토큰 하나를 MCP 서버에 넘기는 구조는 피해야 합니다.

## tracing은 사고 대응의 기본 자료다

MCP 통합에서 tracing은 선택 기능이 아닙니다. 에이전트가 어떤 MCP 서버를 발견했는지, 어떤 도구를 호출했는지, 어떤 인자를 넘겼는지, 도구가 무엇을 반환했는지, 승인이나 차단이 어디서 발생했는지 남겨야 합니다. 그래야 문제 발생 시 원인을 추적할 수 있습니다.

예를 들어 에이전트가 잘못된 저장소 이슈를 닫았거나, 고객에게 부정확한 메일을 보냈거나, 내부 문서를 외부 답변에 섞었다면 최종 답변만으로는 원인을 알기 어렵습니다. 도구 선택, 입력 인자, 중간 응답, 승인 여부를 봐야 합니다.

다만 trace에는 민감 정보가 포함될 수 있습니다. 검색된 문서, 사용자 질문, 도구 응답, API 결과가 그대로 남으면 로그 저장소가 새로운 위험 지점이 됩니다. tracing을 켤 때는 마스킹, 보관 기간, 접근 권한, 샘플링 정책을 함께 정해야 합니다.

## 프로덕션 도입 체크리스트

첫째, MCP 서버 목록을 자산으로 관리합니다. 누가 소유하고, 어떤 데이터에 접근하며, 어떤 인증 방식을 쓰는지 기록해야 합니다. 둘째, 도구 설명을 검토합니다. 모델은 도구 설명을 보고 선택하므로 부정확하거나 과장된 설명은 곧 행동 오류로 이어질 수 있습니다.

셋째, 업무별 도구 allowlist를 만듭니다. 같은 에이전트라도 고객 지원, 개발 운영, 문서 검색, 재무 처리에서 필요한 도구는 다릅니다. 넷째, 읽기와 쓰기 권한을 분리합니다. 상태 변경 도구는 승인, 재확인, 감사 로그를 필수로 둡니다.

다섯째, MCP 서버 장애를 정상 시나리오로 다룹니다. 서버가 느리거나 응답하지 않거나 잘못된 데이터를 줄 수 있습니다. 타임아웃, 재시도, 대체 경로, 사용자 안내 문구가 필요합니다. 여섯째, trace를 평가 데이터로 사용합니다. 어떤 도구를 잘못 골랐는지, 어떤 승인에서 막혔는지, 어떤 서버가 지연을 만들었는지 정기적으로 봐야 합니다.

오늘 기준으로 정리하면 세 가지입니다.

1. MCP 서버는 에이전트의 외부 시스템 접근 경계이므로 신뢰와 권한을 먼저 설계해야 합니다.
2. 도구는 많이 노출할수록 좋은 것이 아니라 업무별로 좁게 열고 쓰기 작업은 승인해야 합니다.
3. tracing, 감사 로그, 도구 필터링 없이는 MCP 기반 에이전트를 프로덕션에서 안정적으로 운영하기 어렵습니다.

MCP는 에이전트 통합을 빠르게 만드는 좋은 기반입니다. 하지만 표준 프로토콜이 보안 정책을 대신해 주지는 않습니다. 실제 품질은 어떤 서버를 신뢰하고, 어떤 도구를 숨기고, 어떤 작업을 승인받고, 어떤 실행 기록을 남기는지에서 결정됩니다.
