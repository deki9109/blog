AI 제품을 만들 때 가장 자주 막히는 지점은 모델이 아니라 데이터입니다. 실제 고객 대화, 의료 기록, 금융 거래, 내부 문서, 장애 로그는 유용하지만 그대로 개발·테스트·공유하기 어렵습니다. 개인정보와 보안 규정, 데이터 접근 권한, 품질 문제, 희귀 사례 부족이 모두 발목을 잡습니다.

이때 합성 데이터가 선택지로 올라옵니다. 합성 데이터는 실제 데이터를 직접 복사하는 대신 통계적 특성, 업무 패턴, 예외 상황을 흉내 내도록 생성한 데이터입니다. 모델 평가용 대화, 함수 호출 시나리오, 고객 지원 케이스, 사기 탐지 샘플, UI 테스트 데이터처럼 실제 데이터만으로 충분히 모으기 어려운 영역에서 특히 유용합니다.

![민감한 실제 데이터가 개인정보 보호 계층을 거쳐 합성 데이터로 변환되고 AI 학습·테스트·시뮬레이션 워크플로에 공급되는 이미지](/images/2026-08-16-synthetic-data-governance.png)

## 합성 데이터는 익명 데이터와 같지 않다

가장 먼저 정리해야 할 점은 합성 데이터가 자동으로 개인정보 위험을 없애지 않는다는 것입니다. 생성 방식에 따라 실제 개인의 패턴이나 희귀 조합이 그대로 남을 수 있고, 공격자가 다른 데이터와 결합해 개인을 추론할 가능성도 있습니다. 단순히 이름과 이메일을 바꿨다고 안전한 데이터가 되는 것은 아닙니다.

영국 ICO의 익명화 guidance는 개인을 식별할 위험을 충분히 낮추는지, 처리 목적과 위험에 맞는 기술적·조직적 조치를 갖췄는지 평가해야 한다고 설명합니다. 합성 데이터도 같은 관점이 필요합니다. 식별 가능성, 재식별 위험, 민감 속성 노출, 원본 데이터와의 과도한 유사성을 테스트해야 합니다.

따라서 합성 데이터를 만들 때는 목적을 먼저 정해야 합니다. 모델 학습용인지, 평가용인지, 데모용인지, 외부 공유용인지에 따라 허용 가능한 위험과 필요한 품질이 다릅니다. 외부 공유용 데이터는 내부 테스트용 데이터보다 훨씬 엄격한 프라이버시 검증이 필요합니다.

## 품질은 원본과 비슷함만으로 판단할 수 없다

좋은 합성 데이터는 실제 데이터와 어느 정도 비슷해야 합니다. 하지만 너무 비슷하면 개인정보 위험이 커지고, 너무 다르면 AI 시스템을 제대로 테스트하지 못합니다. 이 균형이 어렵습니다. 통계적 유사성, 업무 규칙 일치, 예외 사례 포함, 민감 속성 분포, 라벨 품질을 따로 봐야 합니다.

예를 들어 고객 상담 AI 평가셋을 만든다면 단순히 자연스러운 대화가 많다고 충분하지 않습니다. 환불 정책을 잘못 이해한 요청, 화난 고객, 중복 주문, 개인정보 삭제 요청, 상담원 이관이 필요한 상황처럼 실제 운영에서 중요한 케이스가 포함돼야 합니다. 합성 데이터가 쉬운 예제만 만들면 모델은 실전에서 약해집니다.

Microsoft의 Azure AI Foundry 관련 자료도 합성 데이터가 fine-tuning과 evaluation에서 데이터 부족, 민감 데이터 제한, 다양한 시나리오 생성 문제를 완화할 수 있다고 설명합니다. 다만 이 효과는 생성한 데이터가 목표 업무를 정확히 반영하고, 별도 평가로 품질을 검증할 때 의미가 있습니다.

## 운영에서는 데이터 계보와 승인 기록이 필요하다

합성 데이터도 운영 자산입니다. 누가 어떤 원본에서 만들었는지, 어떤 생성 프롬프트와 모델을 썼는지, 어떤 필터와 후처리를 거쳤는지, 어떤 검증을 통과했는지 기록해야 합니다. 그래야 나중에 모델 성능이 바뀌거나 편향 문제가 발견됐을 때 원인을 추적할 수 있습니다.

데이터 계보가 없으면 합성 데이터는 빠르게 통제 불가능한 파일 묶음이 됩니다. 같은 이름의 평가셋이라도 생성 방식이 바뀌면 결과가 달라질 수 있습니다. 평가셋 버전, 생성 설정, 샘플링 기준, 제외 규칙, 승인자, 사용 가능한 목적을 명확히 남겨야 합니다.

GOV.UK의 합성 데이터 윤리 guidance는 합성 데이터 사용에서 안전성, 보안, 투명성, 설명 가능성, 사회적 영향 같은 윤리적 고려가 필요하다고 정리합니다. 이 관점은 기업 AI에도 그대로 적용됩니다. 합성 데이터가 실제 사람을 직접 포함하지 않더라도, 그 데이터로 만든 모델이 실제 사람에게 영향을 줄 수 있기 때문입니다.

## 먼저 적용할 곳과 피해야 할 곳

합성 데이터는 모든 데이터 문제의 해답이 아닙니다. 먼저 적용하기 좋은 곳은 테스트와 평가입니다. 개인정보가 포함된 원본 로그를 그대로 공유하지 않고도, 대표 시나리오와 경계 조건을 만들어 개발자가 반복 테스트할 수 있습니다. 에이전트 도구 호출, 고객 응대, 장애 대응, 문서 검색 품질 평가에 특히 적합합니다.

두 번째는 희귀 사례 보강입니다. 실제 데이터에서 거의 나오지 않지만 실패하면 큰 문제가 되는 케이스를 의도적으로 만들 수 있습니다. 사기 패턴, 안전 정책 위반 요청, 잘못된 파일 권한, 다국어 입력, 낮은 품질의 이미지나 음성 같은 케이스가 여기에 해당합니다.

반대로 합성 데이터만으로 최종 성능을 판단하면 위험합니다. 실제 운영 데이터와 분포가 다르면 모델이 과대평가될 수 있습니다. 특히 의료, 금융, 채용, 신용, 법률처럼 개인에게 큰 영향을 주는 영역에서는 실제 검증 데이터, 도메인 전문가 검토, 법적 검토, 모니터링이 함께 필요합니다.

## 합성 데이터 파이프라인의 최소 기준

첫째, 목적 제한입니다. 합성 데이터를 왜 만드는지, 어디에 쓸 수 있고 어디에는 쓰면 안 되는지 명확히 해야 합니다. 학습용, 평가용, 데모용, 외부 공유용을 구분해야 합니다.

둘째, 프라이버시 검증입니다. 원본과 지나치게 유사한 샘플, 희귀 개인 특성 조합, 민감 정보 복원 가능성을 검사해야 합니다. 필요하면 차등 개인정보보호나 추가 익명화 기법을 검토해야 합니다.

셋째, 품질 검증입니다. 통계적 유사성뿐 아니라 업무 규칙, 라벨 정확도, 편향, 커버리지, 실제 운영 성능과의 상관성을 봐야 합니다. 합성 데이터로 좋아진 모델이 실제 데이터에서도 좋아지는지 별도 확인해야 합니다.

넷째, 계보와 승인입니다. 생성 모델, 프롬프트, 원본 범위, 필터, 검증 결과, 승인자를 기록해야 합니다. 데이터셋 버전이 바뀌면 모델 평가 결과도 함께 추적해야 합니다.

![데이터팀, 보안팀, 제품팀이 합성 데이터의 개인정보 위험, 커버리지, 편향, 모델 평가 지표를 검토하는 회의 이미지](/images/2026-08-16-synthetic-data-governance-sub2.png)

오늘 기준으로 정리하면 세 가지입니다.

1. 합성 데이터는 민감 데이터 접근 제한과 희귀 테스트 케이스 부족을 줄이는 데 유용합니다.
2. 하지만 합성 데이터는 자동으로 익명 데이터가 아니며, 재식별 위험과 원본 유사성 검증이 필요합니다.
3. 운영 자산으로 쓰려면 목적 제한, 품질 평가, 편향 검토, 데이터 계보, 승인 기록을 함께 관리해야 합니다.

AI 개발에서 합성 데이터는 속도를 높이는 도구입니다. 하지만 검증 없는 합성 데이터는 잘못된 자신감을 만들 수 있습니다. 앞으로 중요한 역량은 데이터를 많이 생성하는 능력이 아니라, 생성한 데이터가 안전하고 목적에 맞으며 실제 운영 성능을 설명할 수 있는지 증명하는 능력입니다.
