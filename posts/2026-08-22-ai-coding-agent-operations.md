AI 코딩 도구의 중심이 자동완성에서 에이전트로 이동하고 있습니다. 예전에는 모델이 함수 한 조각을 제안했다면, 지금의 코딩 에이전트는 저장소를 읽고, 관련 파일을 찾고, 코드를 수정하고, 테스트를 실행하고, 커밋 전 검증까지 이어갑니다. 개발자는 답변을 받는 사람이 아니라 작업을 위임하고 결과를 검토하는 운영자가 됩니다.

이 변화에서 핵심은 모델 성능만이 아닙니다. 같은 모델도 저장소 지침, 권한 설정, 테스트 명령, 리뷰 규칙, 배포 경계가 있느냐에 따라 결과가 크게 달라집니다. 코딩 에이전트는 사람 개발자처럼 맥락을 필요로 하지만, 사람보다 훨씬 명시적인 운영 기준을 요구합니다.

## 저장소 지침은 선택이 아니라 기본 인프라다

코딩 에이전트가 반복해서 같은 실수를 한다면 대부분 프롬프트 문제가 아니라 시스템화되지 않은 지식 문제입니다. 프로젝트 구조, 빌드 명령, 테스트 범위, 코드 스타일, 금지된 파일, 배포 전 확인 사항은 매번 채팅으로 설명할 내용이 아닙니다. 저장소 안에 지속적으로 읽히는 지침으로 남겨야 합니다.

OpenAI Codex는 `AGENTS.md`를 통해 저장소별 지침을 줄 수 있고, Anthropic Claude Code는 `CLAUDE.md`와 규칙 파일을 통해 프로젝트 컨텍스트를 관리합니다. Google Gemini Code Assist의 agent mode도 IDE 워크스페이스, 도구 응답, 컨텍스트 파일을 활용해 작업을 진행합니다. 도구마다 파일명과 범위는 다르지만 원칙은 같습니다. 에이전트가 매번 알아야 할 것은 코드 옆에 있어야 합니다.

좋은 지침 파일은 길지 않아야 합니다. "품질 좋게 작성" 같은 추상 문장보다 "API 핸들러는 이 디렉터리에 둔다", "커밋 전 이 명령을 실행한다", "마이그레이션 파일은 직접 수정하지 않는다"처럼 검증 가능한 규칙이 낫습니다. 지침은 모델을 더 똑똑하게 만드는 문서가 아니라, 실수 가능성을 줄이는 운영 계약입니다.

## 권한 경계가 없으면 자동화가 위험해진다

코딩 에이전트는 파일 읽기, 파일 수정, 셸 명령 실행, 네트워크 접근, 외부 도구 호출을 할 수 있습니다. 이 능력이 생산성을 만들지만 동시에 위험도 만듭니다. 잘못된 삭제 명령, 과도한 네트워크 접근, 민감 파일 노출, 의도하지 않은 배포 명령은 모두 권한 설계 문제입니다.

따라서 권한은 기능별로 나눠야 합니다. 읽기 전용 탐색은 넓게 허용할 수 있지만, 파일 수정과 셸 실행은 작업 디렉터리와 명령 범위를 제한해야 합니다. 배포, 비밀값 접근, 데이터베이스 변경, 대량 삭제 같은 작업은 승인 절차를 거쳐야 합니다. 권한은 에이전트의 의도를 믿는 문제가 아니라 실패했을 때 피해 범위를 제한하는 장치입니다.

Google의 agent mode 문서는 읽기 작업과 변경 작업의 승인 흐름을 구분하고, 사용자가 계획과 도구 사용을 승인하거나 조정할 수 있다고 설명합니다. Claude Code도 권한 규칙과 deny 설정을 제공합니다. 실제 운영에서는 이런 기본 기능 위에 조직의 보안 정책, CI 권한, 비밀 관리, 네트워크 허용 범위를 연결해야 합니다.

## 검증 루프는 사람이 아니라 시스템이 먼저 수행해야 한다

에이전트가 만든 코드는 그럴듯해 보일 수 있습니다. 그러나 그럴듯함은 검증이 아닙니다. 빌드, 타입 체크, 단위 테스트, 통합 테스트, 린트, 보안 스캔, 스냅샷 또는 시각 검증처럼 프로젝트가 요구하는 확인 절차를 자동으로 실행해야 합니다. 사람 리뷰는 그 다음입니다.

검증 명령은 지침 파일에 넣어야 하고, 가능하면 CI와 동일해야 합니다. 로컬에서 통과했지만 CI에서 실패하는 명령은 신뢰도를 떨어뜨립니다. 반대로 너무 큰 테스트만 강제하면 에이전트가 작은 변경에도 오래 걸리고 비용이 커집니다. 변경 범위에 맞는 최소 검증과 릴리스 전 전체 검증을 구분하는 것이 현실적입니다.

중요한 점은 실패를 숨기지 않는 것입니다. 에이전트가 테스트 실패를 만났을 때 파일을 되돌리거나 대충 우회하면 안 됩니다. 실패한 명령, 실패 원인, 수정 여부, 남은 위험을 그대로 남겨야 합니다. 코딩 에이전트 운영의 품질은 성공한 작업보다 실패를 어떻게 보고하는지에서 드러납니다.

## 서브에이전트는 병렬 처리보다 책임 분리가 먼저다

최근 코딩 에이전트 환경은 서브에이전트와 다중 에이전트 워크플로를 강조합니다. 하지만 여러 에이전트를 동시에 돌린다고 자동으로 품질이 좋아지지는 않습니다. 책임이 겹치면 서로 다른 변경을 만들고, 리뷰 비용이 늘고, 최종 판단이 흐려질 수 있습니다.

서브에이전트가 유용한 경우는 책임이 명확할 때입니다. 한 에이전트는 테스트 실패 원인을 조사하고, 다른 에이전트는 문서와 릴리스 노트를 확인하고, 또 다른 에이전트는 UI 회귀 스크린샷을 점검하는 식입니다. 코드 수정 권한은 좁게 주고, 최종 통합은 하나의 주 에이전트나 사람 리뷰어가 맡는 편이 안전합니다.

OpenAI Codex 문서는 서브에이전트를 작업별로 구성할 수 있는 기능으로 다룹니다. 이 기능을 생산적으로 쓰려면 "더 많이 병렬화"가 아니라 "누가 무엇을 판단하는가"를 먼저 정해야 합니다. 에이전트 수가 아니라 책임 경계가 운영 품질을 결정합니다.

## 감사 가능성이 곧 신뢰성이다

코딩 에이전트가 실제 제품 저장소에서 일하려면 결과만 남기면 부족합니다. 어떤 지시를 받았는지, 어떤 파일을 읽었는지, 어떤 명령을 실행했는지, 어떤 변경을 만들었는지, 어떤 테스트를 통과했는지 추적할 수 있어야 합니다. 감사 로그는 보안팀만을 위한 것이 아니라 디버깅과 책임 분리의 기본 자료입니다.

특히 자동 커밋이나 자동 PR 생성이 들어가면 커밋 메시지와 PR 본문이 중요합니다. 변경 의도, 검증 명령, 실패한 검증, 사람이 확인해야 할 부분을 남겨야 합니다. 에이전트가 만든 변경은 코드만 보면 안 됩니다. 작업 기록까지 함께 봐야 합니다.

운영 기준을 세울 때는 세 가지 질문으로 시작하면 됩니다.

1. 에이전트가 항상 읽어야 하는 프로젝트 지식은 어디에 있는가?
2. 에이전트가 할 수 없는 작업과 승인이 필요한 작업은 무엇인가?
3. 커밋이나 배포 전에 반드시 통과해야 하는 검증은 무엇인가?

오늘 기준으로 정리하면 세 가지입니다.

1. AI 코딩 에이전트의 성능은 모델만이 아니라 저장소 지침, 권한, 테스트 체계에 좌우됩니다.
2. 자동화가 강해질수록 승인 경계와 감사 로그가 더 중요해집니다.
3. 서브에이전트와 병렬 작업은 책임 분리가 명확할 때만 실제 생산성을 만듭니다.

코딩 에이전트는 개발자를 대체하는 단일 버튼이 아닙니다. 잘 설계된 개발 시스템 안에서 반복 작업을 맡고, 탐색을 빠르게 하고, 검증 가능한 변경을 만드는 운영 구성요소입니다. 앞으로 팀의 차이는 어떤 모델을 쓰는가보다, 에이전트가 일할 수 있는 저장소와 검증 체계를 얼마나 잘 만들어 두었는가에서 갈릴 가능성이 큽니다.
