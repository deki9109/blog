AI 에이전트를 제품에 넣을 때 가장 흔한 착각은 최종 답변만 보면 품질을 알 수 있다고 보는 것입니다. 일반 챗봇이라면 답변의 정확성, 문체, 근거 표시가 핵심 평가 대상입니다. 하지만 에이전트는 다릅니다. 검색, 데이터베이스 조회, 결제, 티켓 생성, 코드 실행, 외부 API 호출 같은 행동을 합니다. 답변이 그럴듯해도 중간 경로가 틀렸다면 실제 제품에서는 장애나 보안 문제가 됩니다.

따라서 에이전트 평가는 "무슨 말을 했는가"에서 "어떤 절차로 그 답에 도달했는가"로 확장되어야 합니다. Google ADK 문서도 에이전트 평가는 최종 응답뿐 아니라 trajectory, 즉 도구 선택과 실행 경로를 함께 봐야 한다고 설명합니다. OpenAI Agents SDK 역시 도구 호출, 핸드오프, 가드레일, 모델 생성 과정을 tracing으로 기록할 수 있게 합니다.

## 최종 답변 채점만으로는 부족하다

최종 답변 평가는 여전히 필요합니다. 사용자의 질문에 맞는지, 사실과 일치하는지, 말투가 적절한지, 민감한 내용을 안전하게 처리했는지 봐야 합니다. 하지만 이 방식만으로는 에이전트의 핵심 위험을 놓칩니다.

예를 들어 고객 지원 에이전트가 "환불 처리되었습니다"라고 답했다고 가정합니다. 답변만 보면 친절하고 정확해 보일 수 있습니다. 그러나 실제로는 주문 상태를 조회하지 않았거나, 인증 전에 환불 API를 호출했거나, 실패한 툴 호출을 성공으로 착각했을 수 있습니다. 이런 문제는 최종 문장만 읽어서는 드러나지 않습니다.

에이전트 품질의 많은 부분은 중간 단계에 있습니다. 어떤 도구를 선택했는지, 호출 순서가 맞는지, 실패를 재시도했는지, 근거 데이터가 충분했는지, 위험한 행동 전에 확인을 받았는지 봐야 합니다. 이 실행 경로가 평가 대상이 되어야 프로덕션 회귀를 잡을 수 있습니다.

## trajectory 평가는 업무 규칙을 검증한다

trajectory 평가는 에이전트가 문제를 해결하는 과정을 평가합니다. 단순히 답이 맞았는지가 아니라, 그 답에 도달하기 위한 단계가 제품 규칙을 지켰는지 보는 방식입니다. 고객 인증 후 계정 조회, 재고 확인 후 주문 생성, 정책 조회 후 환불 안내처럼 순서가 중요한 업무에 특히 필요합니다.

이 평가는 테스트 케이스를 더 구체적으로 만듭니다. "배송 날짜를 물으면 정확히 답한다"보다 "주문 ID를 확인하고, 사용자 인증을 통과한 뒤, 배송 API를 호출하고, API 응답에 근거해 답한다"가 더 좋은 기준입니다. 이렇게 해야 모델이 기억이나 추측으로 답하는 일을 막을 수 있습니다.

Google ADK의 평가 문서는 에이전트 평가를 최종 응답 평가와 trajectory/tool use 평가로 나눕니다. 이 구분은 실무적으로 중요합니다. 최종 응답은 사용자 경험을 보고, trajectory는 업무 규칙과 시스템 안전성을 봅니다. 둘 중 하나만 통과해서는 충분하지 않습니다.

## tracing은 디버깅 로그가 아니라 평가 데이터다

많은 팀이 tracing을 장애 분석용 로그로만 봅니다. 에이전트에서는 tracing이 평가 데이터의 기반이 됩니다. 어떤 모델 호출이 있었는지, 어떤 도구가 호출됐는지, 도구 입력과 출력이 무엇이었는지, 가드레일이 언제 실행됐는지, 핸드오프가 발생했는지 기록해야 나중에 평가할 수 있습니다.

OpenAI Agents SDK의 tracing 문서는 에이전트 실행, 모델 턴, 도구 호출, 가드레일, 핸드오프, 음성 입출력 같은 이벤트를 span으로 기록한다고 설명합니다. 이 구조는 단순한 로그보다 유용합니다. 실행 단계를 계층적으로 볼 수 있고, 실패 지점을 찾고, 배포 전후 행동 변화를 비교할 수 있기 때문입니다.

다만 tracing에는 민감 정보가 포함될 수 있습니다. 사용자 입력, 도구 응답, 계정 정보, 내부 정책, API 결과가 trace에 남을 수 있습니다. 운영 환경에서는 수집 범위, 마스킹, 보관 기간, 접근 권한을 명확히 해야 합니다. 평가를 위해 모든 데이터를 무기한 저장하는 방식은 위험합니다.

## 가드레일은 평가와 함께 설계해야 한다

가드레일은 에이전트 실행 전후 또는 도구 호출 경계에서 위험을 줄이는 장치입니다. 입력이 악의적인지, 출력이 정책을 위반하는지, 도구 호출이 허용된 범위인지 검사할 수 있습니다. OpenAI Agents SDK 문서는 입력, 출력, 도구 가드레일과 tripwire 개념을 제공합니다.

중요한 점은 가드레일을 나중에 붙이는 필터로만 보면 안 된다는 것입니다. 가드레일은 평가 케이스와 연결되어야 합니다. 어떤 입력에서 차단되어야 하는지, 어떤 도구 호출이 거부되어야 하는지, 어떤 출력이 수정 또는 중단되어야 하는지 테스트해야 합니다.

예를 들어 내부 관리자 도구를 호출하는 에이전트라면 "사용자가 권한이 없을 때 도구를 호출하지 않는다", "민감 필드를 외부 응답에 포함하지 않는다", "확인 없이 상태 변경 도구를 호출하지 않는다" 같은 케이스가 필요합니다. 이 테스트는 답변 채점보다 시스템 계약에 가깝습니다.

## 운영 지표는 실패 유형별로 나눠야 한다

에이전트 운영 지표는 단순 성공률 하나로 충분하지 않습니다. 최종 답변 실패, 도구 선택 실패, 도구 호출 실패, 근거 부족, 권한 위반, 가드레일 차단, 사용자 중단, 인간 상담원 전환을 분리해서 봐야 합니다. 그래야 어떤 부분을 고쳐야 하는지 알 수 있습니다.

최종 답변 품질이 낮다면 프롬프트, 모델, 근거 제공 방식을 봐야 합니다. 도구 선택이 틀렸다면 라우팅 기준이나 도구 설명을 봐야 합니다. 도구 호출 실패가 많다면 API 안정성, 입력 스키마, 재시도 정책을 봐야 합니다. 가드레일 차단이 늘었다면 실제 공격이 늘었는지, 정상 요청을 과하게 막는지 구분해야 합니다.

배포 전에는 작은 평가 세트를 만들어야 합니다. 핵심 업무 흐름, 실패 케이스, 권한 경계, 악의적 입력, 애매한 사용자 요청을 포함합니다. 배포 후에는 실제 trace에서 실패 유형을 샘플링해 평가 세트를 보강해야 합니다. 에이전트 평가는 한 번 만든 벤치마크가 아니라 운영 중 계속 갱신되는 회귀 테스트입니다.

## 지금 확인할 체크리스트

첫째, 에이전트가 수행하는 핵심 업무를 도구 호출 경로로 정의합니다. 둘째, 최종 답변 평가와 trajectory 평가를 분리합니다. 셋째, tracing을 기본으로 켜고 민감 정보 정책을 함께 둡니다. 넷째, 가드레일이 개입해야 하는 입력, 출력, 도구 호출 케이스를 테스트로 만듭니다.

다섯째, 실패 유형을 분리해 지표화합니다. 여섯째, 실제 운영 trace에서 새 평가 케이스를 주기적으로 추가합니다. 일곱째, 상태 변경 도구에는 인증, 확인, 감사 로그를 필수로 둡니다.

오늘 기준으로 정리하면 세 가지입니다.

1. AI 에이전트 평가는 최종 답변뿐 아니라 도구 사용 경로를 함께 봐야 합니다.
2. tracing은 디버깅 로그가 아니라 평가와 회귀 테스트의 원천 데이터입니다.
3. 가드레일은 별도 필터가 아니라 테스트 가능한 제품 계약으로 설계해야 합니다.

프로덕션 에이전트는 말을 잘하는 모델이 아니라, 올바른 절차로 행동하는 시스템이어야 합니다. 답변이 맞아 보여도 실행 경로가 틀리면 신뢰할 수 없습니다. 평가 기준을 trajectory, guardrail, trace, 최종 응답으로 나눌 때 에이전트 품질을 실제로 관리할 수 있습니다.
