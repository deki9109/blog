데이터센터에서 병목은 항상 CPU나 GPU만은 아닙니다. 대규모 AI 추론, 벡터 검색, 분석 데이터베이스, 캐시, 인메모리 처리처럼 데이터가 커질수록 메모리 용량과 대역폭, 그리고 메모리 비용이 같이 문제가 됩니다. 서버마다 피크 사용량에 맞춰 DRAM을 넉넉히 꽂아두면 안정적이지만, 전체 클러스터 관점에서는 많은 메모리가 놀게 됩니다.

CXL, 즉 Compute Express Link는 이 문제를 다루기 위한 중요한 표준 중 하나입니다. CXL Consortium은 CXL을 프로세서, 메모리 확장 장치, 가속기 사이의 cache-coherent interconnect로 설명합니다. 핵심은 서버 내부에 고정된 메모리만 쓰는 대신, CXL 장치와 스위치를 통해 더 유연한 메모리 확장과 공유 구조를 만들 수 있다는 점입니다.

## 메모리도 구성 가능한 자원이 되고 있다

기존 서버 구성에서는 CPU, GPU, DRAM, 스토리지가 한 장비 안에서 비교적 고정된 비율로 묶입니다. 워크로드가 이 비율과 잘 맞으면 문제가 적습니다. 하지만 실제 운영에서는 어떤 서버는 CPU가 남고 메모리가 부족하며, 어떤 서버는 메모리가 남고 가속기가 병목이 됩니다. 특히 AI 인프라에서는 모델, KV 캐시, 벡터 인덱스, 피처 저장소, 데이터 전처리 버퍼가 서로 다른 메모리 패턴을 만듭니다.

CXL 메모리 확장은 서버에 더 많은 메모리를 붙이는 단순한 용량 확장부터 시작할 수 있습니다. 그다음 단계는 메모리 풀링입니다. 여러 호스트가 CXL 스위치나 패브릭을 통해 공유 메모리 자원을 더 동적으로 배정받는 구조입니다. 이론적으로는 서버마다 최악의 피크에 맞춰 DRAM을 고정 구매하는 대신, 필요한 시점에 필요한 워크로드로 메모리를 옮기는 쪽에 가깝습니다.

SNIA 자료도 CXL 2.0에서 switching과 memory pooling이 메모리 활용 효율과 온디맨드 용량 제공에 연결된다고 설명합니다. 2026년 현재 CXL 4.0 사양은 대역폭을 128GT/s로 높이고 bundled port와 RAS 개선을 포함합니다. 표준은 빠르게 진화하고 있지만, 운영 성숙도는 하드웨어와 OS, 펌웨어, 관리 소프트웨어가 함께 맞아야 합니다.

## 모든 메모리가 같은 메모리는 아니다

CXL을 도입할 때 가장 흔한 오해는 "메모리가 늘어나면 애플리케이션이 그대로 빨라진다"는 것입니다. 실제로는 메모리 위치와 지연 시간이 중요합니다. CPU에 직접 붙은 로컬 DRAM과 CXL-attached memory는 접근 특성이 다를 수 있습니다. 그래서 워크로드를 어떤 메모리 계층에 둘지 결정하는 정책이 필요합니다.

핫 데이터는 로컬 DRAM에 두고, 덜 민감한 데이터나 피크 시점에만 필요한 버퍼는 CXL 메모리에 두는 방식이 현실적입니다. 데이터베이스 버퍼 풀, 분석 쿼리의 중간 결과, 벡터 검색 인덱스의 일부, AI 추론의 캐시성 데이터처럼 후보는 많지만, 모든 데이터를 무조건 외부 메모리로 보내면 지연 시간과 예측 가능성이 나빠질 수 있습니다.

Linux 커널 CXL 문서는 CXL 장치 구성이 하드웨어, BIOS/EFI, OS, 드라이버, 사용자 정책 사이의 복잡한 handoff를 가진다고 설명합니다. 또한 NUMA, memory tier, hotplug, DAX 같은 운영 요소가 함께 등장합니다. 이 말은 CXL이 단순 장착형 업그레이드가 아니라 플랫폼 구성 문제라는 뜻입니다.

## AI 인프라에서 먼저 관심을 받는 이유

AI 워크로드는 메모리 압박이 크고 변화가 빠릅니다. 모델 크기, 컨텍스트 길이, 동시 사용자 수, 벡터 인덱스 크기, RAG 파이프라인의 일시적 피크가 모두 메모리 요구량을 흔듭니다. GPU가 비싸기 때문에 주변 메모리 병목으로 GPU 활용률이 떨어지는 것도 문제가 됩니다.

CXL은 이런 환경에서 두 가지 가능성을 제공합니다. 첫째, 메모리 용량을 더 유연하게 늘려 워크로드를 수용하는 것입니다. 둘째, 비싼 로컬 DRAM을 모든 서버에 과다 배치하는 대신, 더 큰 풀에서 필요한 곳으로 자원을 배정해 활용률을 높이는 것입니다. SNIA의 CXL 관련 세션도 RAG 파이프라인의 피크 메모리 소비와 CXL memory pooling, memory tiering을 비용 절감과 성능 절충 관점에서 다룹니다.

다만 CXL이 GPU 메모리 병목을 직접 모두 해결하는 것은 아닙니다. GPU HBM, CPU DRAM, CXL 메모리, NVMe 스토리지는 지연 시간과 대역폭이 다릅니다. AI 플랫폼팀은 모델 서빙 경로에서 어떤 데이터가 어느 계층에 있어야 하는지 측정해야 합니다. CXL은 메모리 계층을 하나 더 추가하는 기술이지, 모든 계층을 같은 성능으로 만드는 기술은 아닙니다.

## 도입 전 확인할 운영 기준

첫째, 워크로드 프로파일링입니다. 평균 메모리 사용량보다 피크 패턴, working set 크기, 지연 시간 민감도, NUMA 영향, 페이지 이동 비용을 봐야 합니다. CXL 메모리에 적합한 데이터와 로컬 DRAM에 남아야 할 데이터를 구분해야 합니다.

둘째, 플랫폼 호환성입니다. CPU, 메인보드, BIOS/UEFI, OS 커널, 드라이버, CXL 장치, 스위치, 관리 소프트웨어가 함께 검증돼야 합니다. 특정 하드웨어를 꽂는 것만으로 운영 가능한 memory pool이 자동으로 생기지 않습니다.

셋째, 관측성입니다. 어떤 워크로드가 어느 메모리 계층을 쓰는지, 지연 시간과 대역폭이 어떻게 변하는지, 오류와 RAS 이벤트가 어디에서 발생하는지 추적해야 합니다. CXL 4.0에서 RAS 개선이 강조되는 것도 메모리 확장 구조에서는 장애 감지와 격리가 중요하기 때문입니다.

넷째, 실패 모드입니다. 공유 메모리 장치나 스위치에 문제가 생겼을 때 어떤 워크로드가 영향을 받는지, 격리와 롤백이 가능한지, 재부팅 없이 복구할 수 있는지 검토해야 합니다. 메모리를 공유 자원으로 만들수록 장애 범위 관리가 더 중요해집니다.

![데이터센터 운영팀이 서버 랙 앞에서 CXL 메모리 용량, 지연 시간, 워크로드 배치, 비용 예측 대시보드를 검토하는 이미지](/images/2026-08-17-cxl-memory-pooling-sub2.png)

오늘 기준으로 정리하면 세 가지입니다.

1. CXL은 서버 내부에 고정된 DRAM 중심 구조에서 벗어나 메모리를 더 유연하게 확장하고 배치하려는 데이터센터 표준입니다.
2. AI, 벡터 검색, 분석, 데이터베이스처럼 메모리 피크가 큰 워크로드에서 memory pooling과 tiering의 가치가 커질 수 있습니다.
3. 도입 여부는 대역폭 숫자보다 지연 시간, NUMA, OS 지원, 관측성, 장애 격리, 실제 워크로드 프로파일링으로 판단해야 합니다.

CXL의 의미는 단순히 메모리를 더 많이 꽂는 데 있지 않습니다. 서버 자원을 고정된 박스 단위로 사는 방식에서, 메모리를 더 세밀하게 조합하고 운영하는 방식으로 이동하는 데 있습니다. 아직은 하드웨어와 소프트웨어 성숙도를 함께 봐야 하지만, 메모리 비용이 커질수록 CXL은 데이터센터 설계에서 더 자주 검토될 가능성이 높습니다.
