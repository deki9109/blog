WebAssembly는 더 이상 브라우저 안에서만 쓰는 실행 포맷이 아닙니다. 서버, 엣지, 데이터 파이프라인, 확장 기능 플랫폼에서 Wasm을 플러그인 런타임으로 쓰려는 시도가 늘고 있습니다. 이유는 분명합니다. 작은 실행 단위, 빠른 시작, 샌드박스 격리, 여러 언어를 한 호스트 안에서 다룰 수 있다는 장점이 있습니다.

하지만 Wasm 모듈만으로 좋은 플러그인 시스템이 완성되지는 않습니다. 실제 문제는 "어떤 함수가 어떤 타입으로 호출되는가", "호스트 기능을 어디까지 허용하는가", "버전이 바뀌어도 기존 플러그인이 동작하는가"입니다. WebAssembly Component Model과 WASI가 중요한 이유가 여기에 있습니다.

## 모듈보다 계약이 중요하다

기존 Wasm 모듈은 낮은 수준의 실행 단위를 제공합니다. 성능과 이식성에는 강하지만, 서로 다른 언어로 만든 모듈이 자연스럽게 값을 주고받는 문제까지 해결해 주지는 않습니다. 문자열, 레코드, 리스트, 에러 타입, 리소스 핸들 같은 애플리케이션 수준의 타입을 안정적으로 표현하려면 별도의 계약이 필요합니다.

Component Model은 이 지점에 초점을 둡니다. 컴포넌트가 가져오는 기능과 내보내는 기능을 인터페이스로 정의하고, 여러 언어가 그 경계를 기준으로 연결되도록 만듭니다. WIT(WebAssembly Interface Type)는 이 인터페이스를 기술하는 형식으로 쓰입니다. 핵심은 플러그인 작성자가 Rust, Go, JavaScript, Python 같은 언어 선택에 덜 묶이고, 호스트는 명확한 계약을 기준으로 플러그인을 로드할 수 있다는 점입니다.

이 방식은 플러그인 API를 운영하는 팀에 유리합니다. 기존에는 언어별 SDK, FFI 규칙, 직렬화 포맷, 런타임 버전이 복잡하게 얽혔습니다. Component Model을 쓰면 "이 플러그인은 어떤 인터페이스를 구현한다"는 기준으로 배포와 검증을 설계할 수 있습니다. 바이트코드 포맷보다 중요한 것은 API 경계가 문서와 코드 생성의 공통 기준이 된다는 점입니다.

## WASI는 권한을 운영 단위로 만든다

WASI(WebAssembly System Interface)는 Wasm이 브라우저 밖에서 파일, 시간, 난수, 네트워크 같은 시스템 기능을 다루기 위한 표준 인터페이스 계열입니다. 중요한 특징은 호스트 기능을 무작정 열어주는 방식이 아니라, 필요한 capability를 명시적으로 제공하는 방향이라는 점입니다.

플러그인 시스템에서 이 차이는 큽니다. 사용자가 설치한 확장 기능이 모든 파일과 네트워크에 접근할 수 있다면 샌드박스의 의미가 약해집니다. 반대로 플러그인별로 읽을 수 있는 디렉터리, 호출 가능한 서비스, 사용할 수 있는 시간·난수·소켓 기능을 좁게 부여하면 피해 범위를 줄일 수 있습니다.

운영 관점에서는 권한이 문서가 아니라 배포 설정이 되어야 합니다. 어떤 플러그인이 어떤 capability를 요구하는지 검토하고, 배포 파이프라인에서 승인하며, 실행 시점에 호스트가 이를 강제해야 합니다. Wasm을 선택하는 이유가 보안이라면 이 권한 모델까지 함께 설계해야 합니다.

## 플러그인 아키텍처에 잘 맞는 지점

Component Model과 WASI가 특히 잘 맞는 영역은 제품 내부의 확장 기능입니다. 예를 들어 코드 에디터 확장, 데이터 변환 플러그인, 결제·배송 규칙 엔진, 보안 스캐너 룰, 엣지 컴퓨팅 함수, AI 워크플로 도구 같은 곳입니다. 이들은 대체로 짧게 실행되고, 명확한 입출력 계약이 있으며, 호스트가 권한을 통제해야 합니다.

컨테이너도 격리를 제공하지만 플러그인 단위에는 무거울 수 있습니다. 컨테이너는 프로세스, 이미지, 네트워크, 파일 시스템을 중심으로 한 배포 단위입니다. Wasm 컴포넌트는 더 작은 기능 단위를 빠르게 적재하고 제한된 인터페이스로 호출하는 데 강점이 있습니다. 특히 사용자 제공 코드를 실행하거나 여러 고객의 확장 기능을 한 플랫폼에서 운영할 때 매력적입니다.

다만 "컨테이너 대체"라고 단순화하면 안 됩니다. 장시간 실행되는 서비스, 복잡한 네이티브 의존성, 커널 기능에 깊게 기대는 워크로드, 성숙한 운영 도구가 필요한 시스템은 여전히 컨테이너가 더 자연스럽습니다. Wasm은 모든 서버 워크로드의 대체재가 아니라, 경계가 명확한 확장 코드와 격리 실행 단위에 강한 선택지입니다.

## 실제 도입은 버전 관리가 승부처다

플러그인 플랫폼은 한 번 공개하면 API를 쉽게 바꾸기 어렵습니다. Component Model을 쓴다고 이 문제가 사라지지는 않습니다. 오히려 인터페이스가 명확해지는 만큼 버전 정책을 더 엄격히 세워야 합니다.

처음부터 안정 인터페이스와 실험 인터페이스를 분리해야 합니다. 필드 추가, 에러 타입 변경, 리소스 수명 주기, 비동기 호출 방식이 기존 플러그인을 깨뜨리지 않는지 테스트해야 합니다. 호스트는 여러 인터페이스 버전을 동시에 받아들이거나, 어댑터를 통해 이전 플러그인을 계속 실행할 수 있어야 합니다.

배포 파이프라인도 달라집니다. 플러그인을 단순 파일 업로드로 받는 대신, 인터페이스 호환성 검사, 서명 검증, 권한 요청 검토, 샌드박스 테스트, 성능 기준을 통과해야 합니다. 사용자가 만든 코드를 운영 환경에서 실행한다면 "빌드됨"보다 "통제 가능함"이 더 중요합니다.

## 운영에서 확인할 체크리스트

첫째, 플러그인과 호스트의 경계를 먼저 정합니다. 어떤 기능을 확장 가능하게 열 것인지, 어떤 데이터는 절대 넘기지 않을 것인지 결정해야 합니다. 둘째, WIT 같은 인터페이스 정의를 제품 계약으로 취급합니다. 문서, 코드 생성, 테스트, 릴리스 노트가 같은 계약을 바라보게 해야 합니다.

셋째, capability 정책을 배포 절차에 넣습니다. 플러그인이 요구하는 파일, 네트워크, 시간, 난수, 외부 서비스 접근 권한을 사람이 검토하거나 정책 엔진으로 판단해야 합니다. 넷째, 관측성을 플러그인 단위로 분리합니다. 어떤 플러그인이 느린지, 실패하는지, 과도한 리소스를 쓰는지 볼 수 있어야 합니다.

다섯째, 롤백과 격리 전략을 준비합니다. 잘못된 플러그인 하나가 전체 호스트를 멈추지 않도록 타임아웃, 메모리 제한, 호출 횟수 제한, 장애 격리를 둬야 합니다. 여섯째, 네이티브 의존성이 많은 코드는 초기에 무리해서 옮기지 않는 편이 낫습니다. Wasm 도입은 런타임 선택이 아니라 운영 모델 전환입니다.

오늘 기준으로 정리하면 세 가지입니다.

1. Component Model의 핵심 가치는 Wasm 바이트코드가 아니라 언어 중립 인터페이스 계약입니다.
2. WASI는 플러그인이 호스트 기능을 쓰는 방식을 capability 중심으로 제한하게 해 줍니다.
3. 프로덕션 도입의 성패는 샌드박스 자체보다 버전 관리, 권한 승인, 관측성, 롤백 체계에 달려 있습니다.

WebAssembly Component Model은 플러그인 아키텍처를 더 작고, 더 명확하고, 더 통제 가능한 단위로 바꿀 가능성이 큽니다. 다만 그 가능성은 표준 이름을 도입하는 것으로 나오지 않습니다. 인터페이스를 제품 계약으로 보고, 권한을 실행 시점에 강제하며, 플러그인 생명주기를 운영 시스템 안에 넣을 때 실질적인 장점이 생깁니다.
