전자상거래 플랫폼을 운영할 때 가장 까다롭고 중요한 기술적 도전 과제 중 하나는 바로 '재고 관리'입니다. 한정된 수량의 인기 상품을 수만 명의 사용자가 동시에 구매하려고 결제창을 누를 때, 결제는 정상적으로 승인되었으나 상품이 부족해 배송하지 못하는 '오버셀(Oversell)'을 막기 위해 모든 서비스는 임시로 재고를 묶어두는 '재고 예약(Inventory Reservation) 시스템'을 운영합니다.

이 분야에서 가장 대중적으로 사용되는 도구는 메모리 위에서 모든 데이터를 처리하는 초고속 인메모리 데이터베이스인 Redis였습니다. 대규모 결제 트래픽을 빠르게 소화하기에 Redis만 한 적임자가 없었기 때문입니다. 하지만 세계 최대의 이커머스 솔루션인 쇼피파이(Shopify)는 수년간 성공적으로 운영해 오던 Redis 기반의 예약 시스템을 걷어내고, 뜻밖에도 전통적인 관계형 데이터베이스인 MySQL로 시스템을 회귀 및 교체했다는 엔지니어링 리포트를 발표했습니다. 고성능 인메모리 분산 아키텍처가 트렌드인 시대에, 쇼피파이가 '구식'처럼 보이는 MySQL로 돌아간 이유는 무엇일까요?

---

## 1. 분산 데이터 일관성의 한계와 스플릿 브레인

쇼피파이가 Redis에서 MySQL로 마이그레이션을 단행한 가장 결정적인 이유는 **분산 환경에서의 데이터 일관성(Data Consistency) 문제**였습니다. 

기존 아키텍처에서는 결제 진행 중의 '임시 예약 상태'는 빠른 성능을 위해 Redis에 저장했고, 결제가 최종 완료되었을 때의 '실제 영구 장부 차감'은 안정성을 위해 MySQL에 기록했습니다. 즉, 데이터의 상태가 두 개의 서로 다른 데이터베이스에 쪼개져 보관되는 분산 상태(Distributed State)를 유지하고 있었습니다. 

이로 인해 두 DB 간의 원자성(Atomicity)을 보장할 수 없는 '스플릿 브레인(Split-Brain)' 위험에 직면하게 되었습니다. 예를 들어, MySQL 장부에는 재고 차감이 정상 기록되었으나 Redis의 임시 예약 해제 명령이 네트워크 장애로 유실된다면, 시스템은 재고가 여전히 잠겨있다고 판단하여 실제로 제품이 남았음에도 품절로 처리하는 '언더셀(Undersell)'을 겪게 됩니다. 반대로 Redis에서 예약은 해제되었는데 MySQL 기록에 실패하면 오버셀이 발생합니다. 두 저장소를 한 트랜잭션으로 묶는 ACID 보장이 불가능하다는 구조적 한계가 존재했던 것입니다.

---

## 2. MySQL 8 `SKIP LOCKED`로 해결한 병목 현상

이를 극복하기 위해 쇼피파이는 MySQL 8버전의 최신 기능인 **`SKIP LOCKED`** 기능을 적극적으로 활용하는 아키텍처를 설계했습니다. 

보통 관계형 데이터베이스(RDBMS)에서 동시성 제어를 위해 특정 행에 락(Lock)을 걸면 다른 트랜잭션들이 줄을 서서 대기하느라 병목이 생기지만, `SKIP LOCKED` 쿼리를 사용하면 이미 다른 트랜잭션에 의해 락이 걸린 로우(Row)를 대기하지 않고 그냥 건너뛰어 락이 걸리지 않은 다음 가용 로우를 즉시 선택해 예약할 수 있습니다. 

쇼피파이는 이를 위해 상품 하나당 하나의 로우로 관리하며 수량을 차감하던 방식을 탈피해, 재고 유닛 1개당 하나의 로우로 매핑하는 'Unit-per-row' 모델을 도입했습니다. 그 결과, 수천 개의 트랜잭션이 한 상품에 동시에 몰려도 서로 다른 재고 로우를 락 경쟁 없이 원자적(Atomic)으로 확보할 수 있게 되었습니다.

## 3. 단순함(Simplicity)이 최고의 확장성이다

쇼피파이의 이번 아키텍처 전환은 웹 서비스와 대규모 트래픽 아키텍처를 설계하는 현대의 수많은 IT 엔지니어들에게 강렬한 메시지를 던집니다. 

첫째, **"단순함(Simplicity)이 최고의 확장성이다"**라는 오래된 격언을 다시금 확인시켜 줍니다. 현대 개발 트렌드는 마이크로서비스 아키텍처(MSA)와 함께 서비스마다 각각 다른 특화 DB(Polyglot Persistence)를 배치하는 분산 시스템을 선호해 왔습니다. 하지만 분산 데이터 아키텍처는 필연적으로 데이터 일관성을 깨뜨리고, 이를 보정하기 위한 엄청난 코딩 복잡도와 디버깅 비용을 수반합니다. 쇼피파이는 분산 시스템을 고도화하는 대신, 하나의 관계형 데이터베이스로 일관성을 단일화하고 데이터베이스 내부의 동시성 쿼리 최적화를 통해 문제를 정공법으로 돌파했습니다.

둘째, **진짜 병목은 데이터베이스 자체의 쿼리 엔진 성능이 아니라 '네트워크 커넥션 자원'**일 수 있다는 점입니다. 쇼피파이는 성능 벤치마크 과정에서 데이터베이스의 CPU가 부족한 것이 아니라, 불필요한 네트워크 왕복(Round-trip)으로 인해 DB 커넥션 풀이 고갈되는 현상이 진짜 스케일링의 한계점임을 밝혀냈습니다. 이에 여러 개의 개별 SQL 쿼리를 `UNION ALL`과 같은 단일 배치 트랜잭션으로 묶어 DB 접속 빈도를 극소화하고 성능을 최적화했습니다. 최신 인프라 기기나 분산 캐시를 무작정 도입하기 전에, 우리가 보유한 고전 RDBMS의 기본 기능과 쿼리 성능을 한계까지 끌어올리는 튜닝이 우선되어야 함을 일깨워 줍니다.

## 4. 실무와 일상에 적용하는 데이터 아키텍처 팁

이러한 데이터베이스 아키텍처 기법과 철학은 우리의 실제 실무 및 업무 개발에 어떻게 응용할 수 있을까요?

### ① 실무 개발: 수강신청, 티켓팅 등 '한정 수량 제어'에 `SKIP LOCKED` 활용하기
만약 사내 인트라넷 시스템에서 세미나 참가 신청 시스템을 만들거나 사내 한정판 IT 기기 대여 시스템을 개발해야 한다고 해보겠습니다. Redis나 분산 락(Distributed Lock) 서버를 따로 띄우고 세팅하는 것은 소규모 팀에게 인프라 유지보수 비용과 배포 관리 차원에서 매우 큰 부담입니다. 
이때 쇼피파이의 기법을 차용해 MySQL(혹은 PostgreSQL)에서 제공하는 `SELECT ... FOR UPDATE SKIP LOCKED` 쿼리를 사용하면 추가적인 인프라 구축 없이 오직 관계형 DB 단독으로 완벽한 일관성과 동시성 처리를 손쉽게 해결할 수 있습니다. 복잡한 분산 동기화 코드를 작성할 시간을 획기적으로 절약하고 비즈니스 논리에만 집중할 수 있어 개발 생산성이 향상됩니다.

### ② 기술 부채 방지: 분산 캐시 도입 전에 '단일 원천 정보(Single Source of Truth)' 정책 고수하기
협업 부서에서 새로운 기능을 요구할 때 "이 기능은 속도가 중요하니 별도 NoSQL이나 Redis에 쌓죠"라는 의견이 쉽게 나옵니다. 하지만 이는 미래의 동기화 에러라는 시한폭탄을 심는 일입니다. 
- 데이터의 변경이 잦고 정합성이 생명인 비즈니스 데이터는 최대한 메인 RDBMS의 단일 트랜잭션 안에서 처리하는 것을 원칙으로 삼아야 합니다.
- 캐시나 임시 저장소는 오직 '조회 성능 개선용(Read-only)'으로만 제한하여 활용하고, 쓰기(Write) 동작이 양쪽으로 갈라지는 구조는 철저히 지양하는 아키텍처 가이드라인을 수립해야 합니다. 이것이 시스템 수명을 늘리고 유지보수 비용을 아끼는 최고의 실무 전략입니다.

## 결론: 시스템에 대한 깊은 이해가 미래를 바꾼다

결국 기술의 유행을 맹목적으로 따르기보다, 우리가 해결하려는 핵심 문제(데이터 정합성)의 본질에 집중하는 것이 훌륭한 엔지니어링의 기본임을 쇼피파이의 사례는 보여줍니다. 

오늘 다룬 내용을 세 줄로 요약해 보겠습니다:
1. 쇼피파이는 Redis(예약)와 MySQL(실장부) 간의 일관성이 깨지는 분산 시스템 문제를 해결하기 위해 시스템을 개편했습니다.
2. MySQL 8의 `SKIP LOCKED` 기능과 재고 유닛 단위 로우 모델을 도입하여 락 대기 병목을 없애고 고성능 ACID 트랜잭션을 확보했습니다.
3. 이를 통해 분산 복잡성을 제거하고 데이터베이스의 원자성을 100% 보장하는 강력하고 단순한 아키텍처를 구현해 냈습니다.

최첨단 분산 도구가 가득한 이 시대에, 때로는 묵묵히 제자리를 지켜온 고전적인 도구들을 다시 깊게 이해하고 튜닝하는 것이 가장 세련된 솔루션이 될 수 있습니다.
