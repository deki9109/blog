생성형 AI 비용은 처음에는 단순해 보입니다. 입력 토큰과 출력 토큰에 단가를 곱하면 됩니다. 하지만 실제 제품에 들어가는 순간 계산은 복잡해집니다. 한 사용자 요청 안에서 검색, 재작성, 도구 호출, 재시도, 요약, 검증 모델 호출이 이어지고, 에이전트는 여러 번 모델을 부를 수 있습니다. 겉으로는 한 번의 대화지만 내부적으로는 여러 비용 이벤트가 쌓입니다.

그래서 AI 비용 관리는 단가표가 아니라 관측성 문제로 봐야 합니다. 어떤 기능이 어떤 모델을 몇 번 호출했는지, 입력과 출력 토큰이 얼마나 발생했는지, 캐시가 얼마나 먹혔는지, 지연 시간과 실패율이 어떻게 변했는지, 품질 개선 대비 비용이 타당한지 추적해야 합니다. 이것이 없으면 비용 최적화는 추측이 됩니다.

## 모델 단가보다 요청 단위 원가가 중요하다

팀이 가장 먼저 보는 것은 모델별 토큰 단가입니다. 단가 비교는 필요하지만 충분하지 않습니다. 실제 의사결정에는 요청 단위 원가가 더 중요합니다. 고객 상담 한 건, 문서 요약 한 건, 코드 리뷰 한 번, 검색 응답 한 번에 총 얼마가 드는지를 알아야 제품 가격과 운영 예산을 맞출 수 있습니다.

요청 단위 원가는 단일 모델 호출보다 넓습니다. 프롬프트에 붙는 시스템 지시문, 검색으로 가져온 문서 조각, 대화 히스토리, 함수 호출 결과, 재시도, 안전성 검사, 평가 호출까지 포함해야 합니다. 출력 토큰이 길어질수록 비용과 지연 시간이 같이 늘고, 긴 컨텍스트를 무조건 붙이면 입력 토큰이 빠르게 커집니다.

따라서 비용 지표는 제품 이벤트와 연결돼야 합니다. 단순히 "이번 달 AI 비용"이 아니라 "고객 지원 자동응답 비용", "세일즈 요약 비용", "개발자 보조 기능 비용"처럼 기능과 팀, 고객 세그먼트 기준으로 볼 수 있어야 합니다. 그래야 비용이 늘었을 때 사용량 증가인지, 프롬프트 변경인지, 모델 변경인지, 재시도 증가인지 판단할 수 있습니다.

## 관측성 표준이 필요한 이유

AI 호출은 일반 API 호출과 다릅니다. HTTP 상태 코드와 응답 시간만으로는 충분하지 않습니다. 입력 토큰, 출력 토큰, 모델 이름, 프롬프트 캐시, 툴 호출, 임베딩, 스트리밍, 재시도, 안전성 필터, 평가 결과 같은 AI 고유 지표가 필요합니다.

OpenTelemetry의 Generative AI semantic conventions는 생성형 AI 시스템의 요청, 응답, 토큰 사용량, 모델, 도구 호출 같은 신호를 구조화해 관측할 수 있는 방향을 제공합니다. 이런 표준화가 중요한 이유는 벤더와 모델이 바뀌어도 같은 방식으로 비용과 품질을 비교해야 하기 때문입니다.

벤더 콘솔만 보면 특정 제공자의 비용은 볼 수 있습니다. 하지만 실제 기업 AI는 여러 모델, 여러 클라우드, 자체 호스팅 모델, 에이전트 프레임워크, 검색 시스템을 함께 씁니다. 공통 trace와 metric이 없으면 한 워크플로의 전체 비용을 연결하기 어렵습니다.

## 비용 최적화는 품질과 함께 봐야 한다

AI 비용을 줄이는 가장 쉬운 방법은 더 싼 모델을 쓰고, 컨텍스트를 줄이고, 출력 길이를 제한하는 것입니다. 하지만 그렇게 하면 품질이 떨어질 수 있습니다. 반대로 고성능 모델을 모든 요청에 쓰면 품질은 좋아질 수 있지만 원가 구조가 무너질 수 있습니다. 따라서 비용 지표는 품질 지표와 같은 화면에서 봐야 합니다.

실무적인 방법은 요청을 분류하는 것입니다. 쉬운 요청은 저렴하고 빠른 모델로 처리하고, 어려운 요청은 고성능 모델이나 사람 검토로 넘깁니다. 반복되는 문서나 시스템 프롬프트는 캐시를 활용하고, 검색 결과는 필요한 만큼만 붙입니다. 실패율이 높은 경로는 재시도 비용이 계속 쌓이므로 품질 개선이 곧 비용 절감이 될 수 있습니다.

FinOps Foundation의 FOCUS 사양은 클라우드 비용 데이터를 일관된 형식으로 정규화하려는 흐름입니다. 생성형 AI도 같은 방향이 필요합니다. 제공자별 청구 항목을 제품, 팀, 기능, 고객, 환경별로 매핑해야 예산과 책임을 명확히 할 수 있습니다.

## 예산 가드레일은 런타임에 있어야 한다

월말 청구서를 보고 대응하면 늦습니다. 생성형 AI는 갑작스러운 사용량 증가, 프롬프트 루프, 에이전트 재시도, 잘못된 배치 작업으로 비용이 빠르게 늘 수 있습니다. 따라서 예산 가드레일은 배포 후 리포트가 아니라 런타임 제어에 들어가야 합니다.

기본 가드레일은 네 가지입니다. 첫째, 사용자·팀·기능별 사용량 한도입니다. 둘째, 요청당 최대 토큰과 최대 도구 호출 횟수입니다. 셋째, 실패나 재시도가 일정 기준을 넘으면 중단하는 회로 차단입니다. 넷째, 고비용 모델 호출에는 정책 기반 승인이나 라우팅 조건을 두는 것입니다.

AWS Bedrock과 Google Cloud Vertex AI 같은 플랫폼은 모델 호출 로그, 모니터링, 비용 확인 기능을 제공합니다. 하지만 플랫폼 기능만으로 충분하다고 보면 안 됩니다. 제품 내부의 사용자 행동, 품질 평가, 비즈니스 KPI와 연결돼야 비용이 의미 있는 지표가 됩니다.

## 팀이 바로 확인해야 할 지표

첫째, 기능별 총 비용과 요청당 비용입니다. 전체 청구액보다 어떤 기능이 비용을 만드는지 먼저 봐야 합니다. 둘째, 입력 토큰과 출력 토큰의 비율입니다. 긴 컨텍스트가 문제인지, 불필요하게 긴 답변이 문제인지 구분할 수 있습니다.

셋째, 캐시 적중률입니다. 반복되는 시스템 프롬프트와 문서 컨텍스트가 많다면 캐시가 비용과 지연 시간을 줄일 수 있습니다. 넷째, 재시도율과 오류율입니다. 실패한 요청도 비용을 만듭니다. 다섯째, 품질 지표입니다. 비용을 줄였는데 사용자 수정률이나 상담원 재작업률이 올라가면 실제 절감이 아닐 수 있습니다.

마지막으로 모델 라우팅 결과를 봐야 합니다. 어떤 요청이 어떤 모델로 갔는지, 라우팅 변경 후 비용과 품질이 어떻게 바뀌었는지 추적해야 합니다. 모델 포트폴리오를 운영한다면 라우팅은 비용 관리의 핵심 제어 지점입니다.

![제품팀, 재무 담당자, AI 플랫폼팀이 생성형 AI 사용량, 지연 시간, 품질, 캐시 적중률, 예산 상태 대시보드를 검토하는 회의 이미지](/images/2026-08-19-ai-cost-observability-sub2.png)

오늘 기준으로 정리하면 세 가지입니다.

1. 생성형 AI 비용 관리는 모델 단가표가 아니라 요청 단위 원가와 워크플로 전체 호출 구조를 보는 문제입니다.
2. 토큰 사용량, 캐시, 지연 시간, 오류율, 품질, 팀별 비용 배분을 공통 관측성 데이터로 남겨야 합니다.
3. 예산 가드레일은 월말 리포트가 아니라 런타임 한도, 라우팅 정책, 재시도 제어 안에 들어가야 합니다.

AI 기능이 많아질수록 비용을 줄이는 팀보다 비용을 설명할 수 있는 팀이 더 강합니다. 설명할 수 있어야 최적화할 수 있고, 품질을 잃지 않으면서 모델과 프롬프트, 캐시, 라우팅을 조정할 수 있습니다. 생성형 AI의 다음 운영 기준은 토큰을 얼마나 썼는지가 아니라, 어떤 가치에 얼마를 썼는지 증명하는 능력입니다.
